# Bank REST API

Модульный backend банковского приложения на Java и Spring Boot.

Проект демонстрирует подходы, которые используются при разработке backend-систем: транзакционная обработка данных, асинхронное взаимодействие через Apache Kafka, Transactional Outbox, JWT-аутентификация, управление схемой БД через Liquibase и идемпотентная обработка сообщений на стороне consumer.

Приложение разделено на два независимых модуля:

* `bank_cards_module` — основная банковская логика;
* `email_module` — сервис отправки email-уведомлений.

Основной акцент проекта сделан не только на CRUD-операциях, но и на решении типичных задач backend и распределённых систем.

# Модули

## `bank_cards_module`

Основной банковский сервис.

Отвечает за:

* регистрацию и управление пользователями;

Отдельный сервис для обработки банковских событий и отправки email-уведомлений.

Модуль не участвует непосредственно в транзакциях основного банковского сервиса.

# Transactional Outbox

Одной из основных архитектурных частей проекта является **Transactional Outbox Pattern**.

При выполнении бизнес-операции часто требуется одновременно:

1. изменить данные в PostgreSQL;
2. отправить событие в Kafka.

Если выполнять эти операции независимо, может возникнуть проблема согласованности.

Например:

```text
Изменение БД
     │
     ▼
  SUCCESS
     
Отправка Kafka
     │
     ▼
   FAILED
```

В результате бизнес-операция уже сохранена, а соответствующее событие не отправлено.

Transactional Outbox решает эту проблему.

Событие сначала сохраняется в таблицу `outbox_event` в рамках **той же транзакции**, что и изменение бизнес-данных.

```text
BEGIN TRANSACTION

    UPDATE card
       SET status = 'BLOCKED'

    INSERT INTO outbox_event (...)

COMMIT
```

Если транзакция откатывается, откатываются обе операции.

Если транзакция успешно завершилась, событие гарантированно осталось в Outbox и может быть опубликовано позже.

---

# Outbox Event

Для хранения событий используется таблица:

```text
outbox_event
```

Событие содержит:

```text
id
eventId
aggregateType
aggregateId
eventType
payload
eventStatus
createdAt
publishedAt
retryCount
lastError
```

Payload хранится в PostgreSQL как `jsonb` и представлен в Java через Jackson `JsonNode`.

Общая модель события:

```java
public record BankEvent(
        UUID eventId,
        AggregateType aggregateType,
        Long aggregateId,
        EventType eventType,
        JsonNode payload,
        LocalDateTime createdAt
) {
}
```

Пример события:

```json
{
  "eventId": "3c7d7c3d-4b3c-4b7d-8f7d-9a1c2d3e4f50",
  "aggregateType": "CARD",
  "aggregateId": 42,
  "eventType": "CARD_CREATED",
  "payload": {
    "cardId": 42,
    "userId": 10,
    "maskedCardNumber": "**** **** **** 1234"
  },
  "createdAt": "2026-08-20T12:30:00"
}
```

# Outbox Publisher

Для публикации событий используется отдельный scheduled publisher.

Он запускается с заданным интервалом:

```java
@Scheduled(cron = "*/10 * * * * *")
```

Алгоритм работы:

1. получить batch новых событий;
2. заблокировать выбранные записи;
3. отправить события в Kafka;
4. успешно отправленные события перевести в `PUBLISHED`;
5. сохранить время публикации;
6. при ошибке увеличить `retryCount`;
7. сохранить информацию об ошибке.

Для выборки используется механизм:

```sql
FOR UPDATE SKIP LOCKED
```

Это позволяет нескольким экземплярам publisher одновременно обрабатывать разные записи, не блокируя друг друга.

Размер batch задаётся через конфигурацию.

---

# Статусы Outbox

Используются следующие состояния:

```text
NEW
PUBLISHED
FAILED
```

### `NEW`

Событие создано, но ещё не опубликовано в Kafka.

### `PUBLISHED`

Событие успешно отправлено.

### `FAILED`

При публикации произошла ошибка.

Дополнительно сохраняется:

* количество попыток;
* последняя ошибка.

# Идемпотентность Consumer

Kafka в типичных сценариях доставки обеспечивает **at-least-once** семантику.

Это означает, что одно и то же сообщение потенциально может быть доставлено consumer повторно.

Например:

```text
Kafka
  │
  ▼
Consumer
  │
  ├── отправил email
  │
  ├── произошёл сбой
  │
  ▼
Kafka повторяет сообщение
  │
  ▼
Consumer получает его снова
```

Без дополнительной защиты пользователь может получить два одинаковых email.

Для решения этой задачи используется таблица:

```text
processed_event
```

В ней хранится `eventId` уже успешно обработанных событий.

Структура:

```sql
CREATE TABLE processed_event
(
    event_id UUID PRIMARY KEY,
    processed_at TIMESTAMP NOT NULL
);
```

Алгоритм:

```text
             eventId
                │
                ▼
        processed_event
                │
        ┌───────┴───────┐
        │               │
     exists           absent
        │               │
        ▼               ▼
      skip           process
                        │
                        ▼
                    send email
                        │
                        ▼
                 save eventId
```

Маркер обработки сохраняется после успешной отправки email.

Таким образом, если SMTP-сервер недоступен или отправка завершается ошибкой, событие не считается обработанным и Kafka может повторить его.

---

# Producer Idempotence и Consumer Idempotency

Это две разные задачи.

### Producer idempotence

Настройка Kafka producer:

```text
enable.idempotence=true
```

защищает от появления дубликатов в Kafka при определённых сценариях повторной отправки producer.

### Consumer idempotency

Таблица:

```text
processed_event
```

защищает бизнес-операцию consumer от повторной обработки одного и того же события.

В данном проекте используются оба уровня защиты как разные механизмы.

# Архитектурные решения

## Почему Transactional Outbox?

Прямая отправка Kafka-сообщения из бизнес-метода может привести к рассинхронизации между БД и Kafka.

Transactional Outbox позволяет сначала надёжно зафиксировать событие в той же транзакции, что и бизнес-изменение.

После этого отдельный publisher отвечает за доставку события в Kafka.

---

## Почему Scheduler, а не Debezium?

Для проекта выбран Scheduled Outbox Publisher вместо Debezium/CDC.

Такой вариант позволяет:

* не добавлять дополнительную инфраструктуру;
* сохранить архитектуру относительно простой;
* явно контролировать механизм retry;
* хранить состояние публикации непосредственно в Outbox;
* наглядно продемонстрировать принцип Transactional Outbox.

При необходимости архитектура может быть расширена до CDC-подхода.

---

## Почему один Kafka topic?

Для проекта используется один topic:

```text
bank-events
```

Тип события определяется через:

```text
eventType
```

Это позволяет не создавать отдельный Kafka topic для каждого типа бизнес-события.

При этом consumer может выбирать необходимую логику обработки в зависимости от `eventType`.

---

## Почему нужна идемпотентность consumer?

Kafka может повторно доставить сообщение.

Поэтому обработка должна учитывать возможность повторной доставки.

`eventId` выступает уникальным идентификатором события, а `processed_event` хранит информацию о событиях, которые уже были успешно обработаны.

# Итоговая архитектура

В основе проекта лежит следующий принцип:

```text
REST API
   │
   ▼
Business Logic
   │
   ▼
Database Transaction
   │
   ├──────────────► Business Data
   │
   └──────────────► Outbox Event
                         │
                         ▼
                  Outbox Publisher
                         │
                         ▼
                       Kafka
                         │
                         ▼
                  Email Consumer
                         │
                         ▼
                  Idempotency
                         │
                         ▼
                       SMTP
```

Таким образом, бизнес-операция не зависит напрямую от доступности Kafka или SMTP-сервера.

Событие сначала фиксируется вместе с бизнес-изменением в базе данных, после чего доставляется асинхронно.

Это позволяет разделить:

**бизнес-логику → публикацию событий → обработку событий → отправку уведомлений.**
